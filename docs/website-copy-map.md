## Proposed changes

- Move the motivation narrative to `/motivation/`. Retain `/benchmarks/storage/#motivation` as a short signpost so existing links still land on useful content.
- Make home explain the product, demos explain the task, benchmarks explain the evidence, and docs explain the API. Replace generic headlines and implementation commentary with specific guidance.
- Use consistent names: OPFS VFS, Volume Explorer, PGlite memory-only storage, memory buffer, disk buffer, synchronization, and volume. Distinguish browser-local persistence from backups.
- Preserve benchmark data, caveats, experimental status, code examples, legal terms and release history. Correct the methodology summary to distinguish Mac and iPhone protocols.
- Add descriptions to pages and docs, a navigable `/sitemap/`, generated XML sitemap, robots discovery, and an `llms.txt` guide with an `llm.txt` alias. Keep internal design studies and embedded demos out of search indexes.

```text
## Connect to a volume

Discovery scans the origin's OPFS root while the panel is open. New volumes appear automatically. Select one to connect:

- **Application owner available:** attach to the compatible worker already serving the volume. The application keeps ownership.

Copy works across volumes; cut and paste is limited to the same volume. Existing destinations are never replaced by these file actions. A failed multi-file copy can leave a partial destination, which the error reports.

Use the **Preview / Editor** tabs to switch views. Text previews wrap long lines and hide line numbers for reading; the editor keeps line numbers and highlights the active line. The header shows **No changes** until you edit, then offers **Save**. Returning to the saved content clears the dirty state. The source editor fills the pane and uses CodeMirror's virtual scrolling and lazy syntax highlighting for recognized languages, including configuration and environment files. Common UTF-8 source and configuration files can be edited up to **16 MiB**, including `.conf`, `.env` and `.env.*`, INI, TOML, JSON, Python, Rust, Go, C/C++, Java, and TypeScript. Files such as `Dockerfile`, `Makefile`, `README`, and `.gitignore` are also supported. Binary data and unknown formats remain read-only. Saving compares the current contents with the version on which the draft began; a concurrent application edit rejects the save instead of silently overwriting it. Use Refresh to reread the tree and file contents. Refresh does not discard drafts.

Previews include Markdown, images, SVG, multipage PDF, text and a bounded hexadecimal fallback. SVG renders as an image, not inline page markup. Markdown does not load remote images. PDF and editor code load on demand. Symbolic links are listed but not followed by file previews. The explorer is limited to 10,000 entries; previews and shell file reads/writes are bounded to 16 MiB per file.

The terminal runs **just-bash**, with file writes checked at the filesystem boundary. It has no network configuration. Each volume connection starts at `/` and keeps its working directory and shell variables between commands, so `mkdir tmp`, `cd tmp`, and `touch note.txt` create `/tmp/note.txt`. Reconnecting starts a new shell session. The prompt shows the current directory, and new output scrolls into view. The shell library reports its final directory through `PWD`; assigning or unsetting `PWD` therefore changes the next command's starting directory. Commands such as `cp` retain shell semantics, including replacing a destination when writes are enabled; the context menu's no-overwrite policy applies to its own actions. Output is retained up to 16,000 characters.

Import validates a ZIP before creating a new volume. It rejects traversal paths, symbolic links, duplicate paths, and file/folder conflicts. Importing into an existing application volume is not supported. A storage failure during writing leaves the partial volume available for inspection.
```

```text
## Where do writes go?

The buffer mode controls how the VFS accesses file contents. Both modes use OPFS storage. A memory buffer is **not** a temporary, memory-only filesystem.

<BufferingDiagram />

## Default settings

Direct mounts and worker clients default to `bufferMode: 'disk'` and `localDurabilityMode: 'balanced'`. Disk mode avoids a full RAM copy of file contents. Balanced mode schedules synchronization about 150 ms after the first dirty change, but a busy or suspended worker can delay it. Continue using explicit `fsync` or volume synchronization at meaningful save points.

For memory caching with explicitly managed synchronization, select `{ bufferMode: 'memory', localDurabilityMode: 'relaxed' }`. Both buffer modes persist to OPFS. The PGlite adapter's separate `relaxedDurability` option is unchanged. See [storage modes explained](/benchmarks/storage/) for the tradeoffs.

## When are changes synchronized?

Buffering chooses the data path. Local durability chooses when the VFS requests a flush of pending changes.

| Local durability    | What triggers synchronization?                                                                                  | What to remember                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `relaxed`           | Explicit synchronization or an orderly close.                                                                   | Your application chooses save points.                                                 |
| `balanced`, default | A timer scheduled about 150 ms after the first dirty change, plus explicit synchronization or an orderly close. | Worker scheduling or suspension can delay the timer. It is not a maximum loss window. |
| `strict`            | Also flushes appended memory-mode recovery-log records immediately.                                             | It does **not** flush every disk-buffered write. Keep explicit save points.           |

<SaveTimeline />

For a direct `OpfsVfs` mount in a dedicated worker, call `vfs.syncSync()` to synchronize the volume. `vfs.fsyncSync(fd)` currently uses the same volume-wide synchronization after validating the file descriptor.

With an initialized worker client, await the asynchronous call:

[Code example: see original source.]

Await `closeVfs()` when finished with the volume. Closing a file descriptor alone is not a substitute for synchronizing the volume. Browser shutdown may interrupt work, so do not rely on a page-close handler as your only save point.

## If a session is interrupted

On the next mount, the VFS checks the volume and attempts recovery before `ready` resolves. A recovery log, also called a write-ahead log or WAL, records changes that may need to be replayed. Recovery cannot promise to restore every unsynchronized write.

The VFS exposes local persistence status, including dirty pages, pending WAL bytes, state, and last error. The default recovery policy salvages recoverable WAL damage; `recoveryMode: 'fail-stop'` lets an application decide instead. Do not automatically delete a volume after a mount error.

Synchronization does not protect against clearing site data or browser storage eviction. Offer an export or backup for important files.

## Switching from memory to disk buffering

A cleanly closed volume can reopen using disk buffering. If a previous session left a nonempty memory recovery log, a disk mount rejects it with `EBUSY` to avoid discarding recoverable changes.

Reopen that volume with `bufferMode: 'memory'`, await `ready`, and successfully await `closeVfs()`. Then reopen it with the disk default. Do not delete recovery logs or reset the volume to bypass the error.
```

```text
## Persistence and limits

Await `vfs.ready` before mounting. Finish guest execution and close its sandbox before closing the SDK or volume. Call `fsyncSync`, `syncSync`, or orderly `closeVfs` at save boundaries. A successful write or file close alone is not a volume checkpoint. Reloading during execution is an abrupt interruption.

Use one owner for each volume. Another tab cannot simultaneously mount the same named volume. The adapter handles ordinary files/directories, binary I/O, append, truncation, rename, live descriptor sizes, and error propagation. It rejects symlinks, hard links, and unsupported file kinds. Arbitrary namespace changes outside the adapter while guest descriptors remain open are unsupported; it refuses an unsafe descriptor unlink instead of deleting a replacement file.

This integration is experimental. Only Chromium has been validated. The full SDK-hosted upstream EdgeJS compatibility run did not pass in either filesystem configuration; this guide makes no claim of full Node.js compatibility. Permissions, very large files, multiple simultaneous guests, and other browsers need further validation. The demo caps program time, captured output, storage, and file previews.
```

```text
<SiteLayout title="Benchmark methodology · OPFS VFS">
<p class="kicker">Benchmarks / methodology</p>
<h1>Benchmark methodology</h1>
<p class="reading-lead">The same work, measured separately from setup. Here is what the runner tests, what stays constant, and where the numbers stop telling the story.</p>
<div class="reading-links"><a href="/benchmarks/run/">Run the benchmarks →</a><a href="/benchmarks/storage/">Understand storage modes →</a></div>
<nav class="reading-nav" aria-label="On this page">
<span>ON THIS PAGE</span>
<a href="#timing">What we time</a>
<a href="#sql-suite">The SQL suite</a>
<a href="#durability">Durability settings</a>
<a href="#comparison">A fair comparison</a>
<a href="#limits">Reading the results</a>
<h2>What we time</h2>
<p>Each backend runs sequentially with deterministic input. The runner separates preparation, initialization, measured work, persistence barriers, and reopen mount time.</p>
<p>This lets you distinguish the cost of starting a database from the cost of using it. Closing the instance and final cleanup are outside the reported timers.</p>
<h2>The PGlite speed-test suite</h2>
<p>The full SQL workload runs the 16 historic cases published in <a href="https://pglite.dev/benchmarks">PGlite's benchmark overview</a>. This is a shared workload descended from SQLite and wa-sqlite, not a formal industry standard.</p>
<p>The unchanged SQL is pinned to <a href="https://github.com/electric-sql/pglite/tree/ae182ff8bd5ba4acb887d6c925d607a1498aa0b5/packages/benchmark/src">upstream commit ae182ff8</a>. Hashes and licenses accompany the <a href="/benchmarks/pglite/README.md">downloadable SQL assets</a>.</p>
<h3>How it runs</h3>
<p>Each complete SQL file goes into one PGlite <code>exec</code> call, in its original order. Every repetition starts with a fresh database. Fetching the SQL is outside the timers.</p>
<p>We omit the upstream live runner's additional 2.1 and 3.1 variants. Case 3.1 creates an index on a different table from the one it inserts into. The 16 included cases are unchanged.</p>
<h3>How we check correctness</h3>
<p>SELECT counts are checked after cases 4, 5, and 7. Before DROP, row counts and sums of both numeric columns and text lengths must match values independently calculated from the fixed SQL.</p>
<p>These checks are outside case timings. Total workload time is the sum of the 16 case timings. Only fully successful runs enter the comparison. Exports retain completed timings from failed or cancelled runs.</p>
<aside class="reading-note"><p>The suite ends by dropping its tables. Reopen checks that they remain absent. To verify retained rows, choose <strong>Insert + query</strong> or <strong>Transaction batch</strong>.</p></aside>
<p>Cancel takes effect between SQL files, after the current file finishes. Cleanup then closes and removes that run's storage.</p>
<h2>Durability settings</h2>
<p>The PGlite durability option applies equally to all four backends. The benchmark's default waits for filesystem synchronization. OPFS VFS buffer and local durability settings are separate and affect only OPFS VFS.</p>
<p>Persistence timing is omitted in relaxed PGlite mode because its sync call can return before the filesystem write completes. Close and reopen still run, but closing time is outside the reported measurements.</p>
<p>We do not override PostgreSQL's <code>synchronous_commit</code> setting. Exports record the effective settings and workload revision.</p>
<p>New to these settings? The <a href="/benchmarks/storage/#durability">storage guide explains buffering and durability</a> in plain language.</p>
<h2>What stays constant</h2>
<li>SQL comparisons use the same PGlite version, schema, dataset, queries, and transaction boundaries.</li>
<li>Filesystem comparisons use the same workload payload, repetitions, and storage options.</li>
<li>Exports record the browser, isolation state, selected configuration, and failed or skipped samples.</li>
<p>Results from different hardware, browser versions, library versions, or durability settings are not directly interchangeable.</p>
<h2>Reading the results</h2>
<li>Cold measurements do not mean browser or operating-system caches were cleared.</li>
<li>An in-memory commit does not have the same persistence guarantee as a completed flush.</li>
<li>A clean close and reopen does not test recovery from a crash or power loss.</li>
<li>A skipped backend is not a zero.</li>
```

```text
<SiteLayout title="Storage modes explained · OPFS VFS">
<p class="kicker">Benchmarks / storage guide</p>

<p class="reading-lead">Storage choices answer different questions: where your data lives, how much memory it uses, and when a change reaches disk. Here is how to read the benchmark settings.</p>

<span>ON THIS PAGE</span>

<h2>Why OPFS VFS exists</h2>
<p>OPFS VFS began with a practical requirement: persistent storage for applications that need synchronous access to many files. During its development, PGlite's access handle pool could not run in macOS Safari. Safari's low limit on open synchronous handles was below the number of files needed by a standard Postgres installation.</p>
<p>Memory-only storage did not meet the persistence requirement. PGlite's IndexedDB backend did, but it loads database files into memory and saves whole changed files. As those files grow, flushing them can become expensive even when a query changes only a small part. That is a tradeoff of this filesystem implementation, not an inherent limit of every IndexedDB application. <a href="https://pglite.dev/docs/filesystems">PGlite documents these storage strategies.</a></p>
<p>Splitting data into chunks or packing files into fewer backing files can address these problems, but doing that inside each application means owning the layout, allocation, metadata, and recovery logic. OPFS VFS provides a reusable filesystem for that work. It maps logical files into a volume and keeps native handle usage bounded as the directory tree grows.</p>
<p>Browser improvements have made AHP usable in more environments, including our iPhone Safari tests. The motivation remains: provide synchronous, persistent file access without tying the number of application files to the size of a native handle pool. Choose between the backends using your workload, memory budget, and durability requirements. The <a href="/benchmarks/">published benchmarks</a> show where their performance differs.</p>
<h3>Adapters and tools for working with files</h3>
<p>We also wanted a library with ready-to-use adapters for different applications. The <a href="/docs/integrations/pglite/">PGlite adapter</a> connects a database to persistent storage. The <a href="/docs/integrations/just-bash/">just-bash adapter</a> brings shell commands, pipes, and scripts to the same files through a POSIX-style filesystem interface. That makes paths and directories useful building blocks for browser editors, document workspaces, and tools that process files.</p>
<p>Developer tools were another missing piece. We built the <a href="/docs/guides/devtools/">OPFS VFS Volume Explorer</a> to browse, preview, and edit files, inspect a running application's storage, and use a shell. A shared filesystem layout lets these tools work across applications without decoding a different chunking scheme for each one.</p>
<h3>Encryption and reactive workflows</h3>
<p>Our requirements also included encryption, which the AHP setup we started with did not provide. That led us to build a premium encryption plugin with passkey-based access to encrypted volumes. We are developing additional plugins, including a subscription plugin intended to let applications react to file changes. The subscription plugin is not available yet.</p>
<p>We see these pieces as useful foundations for AI-assisted browser applications. An assistant can work with documents through familiar file paths and shell operations, while developers inspect the same workspace in the explorer. The <a href="/demos/ai/">local AI demo</a> explores this today. File subscriptions could help keep an interface or a derived view up to date as those files change.</p>
<h2>Where does the data live?</h2>
<p>All four SQL backends run the same PGlite database engine. What changes is the way it stores database files.</p>
<div class="reading-table" role="region" aria-label="Storage backend comparison" tabindex="0">
<caption>The four choices in the PGlite benchmark</caption>
<thead><tr><th scope="col">Backend</th><th scope="col">How it stores files</th><th scope="col">After the session</th></tr></thead>
<tr><th scope="row">PGlite memory</th><td>Temporary working memory, or RAM.</td><td>Gone unless you explicitly export and later restore it.</td></tr>
<tr><th scope="row">PGlite IndexedDB</th><td>Loads files into RAM and saves changed files into the browser's IndexedDB database.</td><td>Saved data can be reopened locally.</td></tr>
<tr><th scope="row">PGlite OPFS AHP</th><td>A pool of open file handles connects database files to OPFS storage.</td><td>Saved data can be reopened locally.</td></tr>
<tr><th scope="row">OPFS VFS</th><td>Maps many logical files into an OPFS volume, using a bounded set of handles.</td><td>Saved data can be reopened locally.</td></tr>
<p>OPFS is the browser's private filesystem for a website. AHP means <em>access handle pool</em>. Those handles let a worker read and write files. PGlite's IndexedDB backend saves whole changed files; it still keeps a working copy in RAM. See <a href="https://pglite.dev/docs/filesystems">PGlite's filesystem guide</a> for backend requirements.</p>
<aside class="reading-note"><p><strong>Memory-only is a speed reference.</strong> It avoids persistent storage work. For an app that should resume after a reload or in the next session, compare the persistent backends with each other.</p></aside>
<h2>OPFS VFS and access handle pools</h2>
<p>Both OPFS VFS and PGlite OPFS AHP provide synchronous filesystem operations inside a worker. An ordinary OPFS VFS volume opens six backing-file handles, independent of the number of virtual files. PGlite AHP keeps handles for database files and a spare pool. The VFS layout reduces handle consumption as the virtual file count grows.</p>
<p>A <a href="https://github.com/WebKit/WebKit/commit/1667e4506835aebe1431586c46888b3139db6e58">WebKit change in August 2025</a> raised the NetworkProcess and GPUProcess file-descriptor limit toward 2,560, subject to system limits. This is a process-wide resource limit, not a guarantee of 2,560 OPFS handles per application or a fixed 1,000-file ceiling. A growing handle pool can still exhaust the available descriptors; the usable count depends on the browser build and other resource use.</p>
<p>AHP completed the published iPhone 17 Pro SQL runs in Safari 26.6.1. A separate user-reported Mac Safari attempt stalled with <code>UnknownError: Invalid platform file handle</code>. The cause and the device's handle limit were not measured. The Mac collection omitted AHP in Safari by protocol; those entries are not measured failures.</p>
<p>Browser support and performance depend on the environment and workload. AHP had the lower iPhone SQL-suite median, while disk-buffered OPFS VFS had the lower iPhone transaction median and lower medians in the Mac Chrome and Firefox comparisons. Neither result establishes a universal speed or durability advantage.</p>
<h2>Memory buffering still uses storage</h2>
<p>The <strong>VFS buffer</strong> setting applies only to OPFS VFS. Both choices use OPFS and can retain files across sessions.</p>
<h3>Memory buffer</h3>
<p>Keeps file contents in RAM for access. Writes also go into an OPFS recovery log, and synchronization copies changed data into the volume. RAM use grows with the files.</p>
<h3>Disk buffer</h3>
<p>Reads and writes the volume's data blocks directly. It avoids keeping a full extra copy of file contents in the VFS, though metadata and the database engine still use RAM.</p>
<p><strong>VFS memory buffering is different from PGlite memory-only storage.</strong> Changing the buffer does not turn persistence off. Both the benchmark and the VFS library default to disk buffering. Memory buffering remains an explicit option.</p>
<h2>When does a change reach disk?</h2>
<p>A write can finish before every change has been flushed to disk. A <em>flush</em> asks the browser to persist pending changes. Local durability controls when OPFS VFS requests that work.</p>
<h3>Relaxed</h3>
<p>Defers flushes to an explicit synchronization request or an orderly close. This can reduce waiting, but unsynchronized work is more exposed to interruption.</p>
<h3>Balanced</h3>
<p>Groups changes and schedules synchronization about 150 milliseconds after the first change. A busy or suspended worker can delay it, so this is not a guaranteed limit on lost work.</p>
<h3>Strict</h3>
<p>With memory buffering, flushes appended file-data and namespace recovery-log records immediately. In the current implementation, strict does not add a flush to every disk-buffered write. Explicit synchronization still matters.</p>
<p>Both the benchmark and the library default to balanced. Relaxed remains available when an application manages synchronization explicitly. These settings describe flush policy, not an absolute guarantee against every kind of crash. See the <a href="/docs/guides/persistence/">persistence API guide</a> and <a href="https://developer.mozilla.org/en-US/docs/Web/API/FileSystemSyncAccessHandle/flush">browser flush documentation</a>.</p>
<h2>PGlite has a separate durability setting</h2>
<p>The benchmark's PGlite durability option controls whether database work waits for filesystem synchronization. It applies to all four SQL backends. The VFS settings above apply only to OPFS VFS.</p>
<p>With default PGlite durability, a query can trigger a VFS synchronization even if the VFS local mode is relaxed. Relaxed PGlite durability avoids waiting on that path; the VFS balanced timer or strict memory-log flushes still apply.</p>
<aside class="reading-note"><p>When integrating PGlite yourself, set <code>relaxedDurability: false</code> on <strong>both PGlite and the OPFS VFS adapter</strong> if you want PGlite synchronization requests to flush the VFS. The adapter defaults to relaxed mode. The benchmark sets both together.</p></aside>
<p>See the <a href="/docs/integrations/pglite/">adapter guide</a> and <a href="https://pglite.dev/docs/api">PGlite API reference</a> for configuration.</p>
<h2>Where to start</h2>
<p>For an app that saves user work, start with <strong>Persistent storage only</strong> enabled. The benchmark's disk buffer, balanced local durability, and default PGlite durability give you a consistent starting point.</p>
<p>Try memory buffering when your files fit comfortably in RAM. Add PGlite memory-only to see the speed of temporary storage. Keep the settings beside the results when comparing runs.</p>
<aside class="reading-note"><p><strong>Switching from memory to disk?</strong> If a disk mount reports a nonempty memory recovery log, reopen with <code>bufferMode: 'memory'</code>, then close the volume successfully before switching to disk. Do not delete the recovery log. See the <a href="/docs/guides/persistence/">buffer-mode troubleshooting</a>.</p></aside>
<p>The benchmark checks a clean close and reopen, then deletes its temporary databases. It does not simulate a crash. The full 16-case SQL suite drops its tables; the quick workloads check retained rows. Read the <a href="/benchmarks/methodology/">methodology</a> for the exact checks.</p>
<h2>Local storage is not a backup</h2>
<p>IndexedDB and OPFS belong to a site's browser storage. Quotas vary, writes can fail when space runs out, and clearing site data removes saved files. Best-effort storage may also be evicted under storage pressure.</p>
<p>A granted browser persistent-storage request helps protect against automatic eviction. It does not prevent a user from deleting data, and it does not copy files to another device. This browser permission is separate from the benchmark's persistence toggle. See <a href="https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria">MDN's storage limits guide</a>.</p>
<p>Applications should synchronize at meaningful save points, handle storage errors, and offer an export or backup for work users cannot afford to lose.</p>
```
