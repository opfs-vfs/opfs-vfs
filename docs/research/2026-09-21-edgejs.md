# EdgeJS without forks

Checked 2026-09-21 against website integration base `0a3b8ad`. Adopted on `codex/edgejs-adapter`; no website, DuckDB or shared stack metadata changes.

## Decision and measured result

Follow-up: the [live OPFS mount experiment](edgejs-live-opfs/README.md) now verifies unchanged EdgeJS against a custom Wasmer SDK and runtime. It includes reproducible patches, live bidirectional access, fresh-runtime persistence and two runtime fixes discovered by the probe. The snapshot adapter below remains the shipped implementation.

Use unmodified `@wasmer/sdk@0.14.0` with `wasmer/edgejs@0.2.0`. The supported `sandbox.fs` API is enough for the existing snapshot-and-sync model. No package patch or fork is required. Direct per-operation OPFS mounts require browser-host implementation work and a JavaScript filesystem-provider API. EdgeJS itself need not change; a reproducible Wasmer host patch or separate host implementation could supply that work without an upstream merge.

The Chromium probe executes `node:fs` reads from OPFS-seeded input, writes a nested result, overwrites a longer file with one byte, and deletes a file. After synchronization, it closes both the OPFS volume and sandbox, reopens the same volume, checks the bytes and deletion, then starts a fresh sandbox and EdgeJS process that reads `edgejs:OPFS-VFS`. Both guest processes exit 0. An outside-workspace sentinel stays unchanged.

```sh
pnpm install
pnpm --filter @opfs-vfs/opfs-vfs exec playwright install chromium
pnpm --filter @opfs-vfs/opfs-vfs test:edgejs
```

The checked-in [probe](../../packages/opfs-vfs/src/__tests__/edgejs.probe.ts) passed in Chromium 147.0.7727.15 with Playwright 1.59.1. The [adapter checks](../../packages/opfs-vfs/src/__tests__/wasmer-adapter.test.ts) cover type replacements, shorter overwrites, stale deletion, failed reads/writes, malformed names, recursion limits, OPFS symlinks and hard-linked outside aliases. An earlier temporary probe also passed with historical `wasmer/edgejs-quickjs@0.0.6` using the original adapter plus a wrapper for the new API. Neither test establishes broader Node compatibility, networking, or other-browser support.

Validation completed: library build and TypeScript checks, repository lint and unused-code checks, all 31 library test files with 559 passing tests, plus the separate real EdgeJS probe. Eight temporary guard mutations were each caught by the adapter tests; the original source was restored. Independent implementation critique returned SHIP.

## Actual filesystem interface and reuse

The new JavaScript API replaces `Directory`, `fromRegistry` and per-run mounts with `new Wasmer()`, `packages.load()`, `sandboxes.create()` and `sandbox.fs`. The filesystem exposes byte reads/writes, directory listing, mkdir, stat, remove and rename. It does not accept an OPFS backend. [Public JavaScript API](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/js/src/index.ts#L1491-L1543).

`OpfsVfsWasmerAdapter` retains the existing copy-in/copy-out model. It reuses the already shipped `OpfsVfsJustBashAdapter` for byte I/O instead of importing the old duplicate VFS method dispatcher. It preloads the source before mutation, validates destination entries, handles type changes and deletions, rejects detectable OPFS links, and recreates destination files to avoid modifying outside hard-link aliases. The [API example](../API.md#edgejs-through-wasmer) shows lifecycle and explicit durability calls.

A target-dependent path bug matters: on a fresh published 0.14.0 sandbox, `fs.readDir('.')` and `fs.readDir('/')` succeed, while `fs.readDir('/workspace')` fails with `entry not found`. The SDK uses Rust `Path::is_absolute()` before stripping `/workspace`. The [release compiler's implementation](https://github.com/rust-lang/rust/blob/923c95cdf5ba65cea505aa2ea829f578e1506ed8/library/std/src/sys/path/unix.rs) returns false on `wasm32-unknown-unknown` because it requires a path prefix that this target never provides. Native-host reasoning about that source therefore predicts the wrong browser behavior. [Release build logs](https://github.com/wasmerio/wasmer-sdk/actions/runs/35180061982/job/105070117136) show fresh compilation with that compiler. The adapter uses relative `.` and relative child paths, supported by both the documentation and the binary. No compatibility patch is needed.

The Rust SDK has a `FileSystem` provider and `SandboxBuilder.mount`, but its JavaScript bindings do not expose that provider. More importantly, the [command implementation](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/rust/src/command.rs#L335-L345) applies external mounts only under `cfg(feature = "sys")`. Browser builds omit this native-only path. A separate wrapper that merely exports `SandboxBuilder.mount` therefore cannot provide browser OPFS mounts. A direct OPFS mount needs browser-host implementation work as well as bindings; it cannot be added by patching only the published JavaScript. [Provider contract](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/rust/src/provider_fs.rs#L147-L168), [Rust mount](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/rust/src/sandbox.rs#L121-L136), [bindings](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/js/bindgen/src/lib.rs).

## Limits and integration boundary

Synchronization requires exclusive access and a stopped guest. It copies the entire tree and holds its bytes in memory. It preserves contents and directories, not file metadata or link identity, and is not transactional on destination failures. Until sync-back and OPFS flush/close finish, guest changes remain memory-only. Files outside the selected OPFS `/workspace` are not part of the copy.

The SDK lacks `lstat` and a symlink directory-entry kind. Sandbox links and special files are unsupported. Temporary guest probes creating absolute symlinks to both `/etc/passwd` and `/workspace/input.txt` made SDK directory listing fail; this is not evidence that every possible link is rejected. Recursion is bounded at 64 levels. Use ordinary file/directory workspaces for this adapter.

Only Chromium was tested. Upstream's [browser compatibility code](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/wasmer-sh/src/browser-compatibility.ts) says Safari lacks required JSPI and Firefox support remains in progress. The [host-engine mode is experimental](https://github.com/wasmerio/edgejs/blob/7027edfa748d9b5e2f6beba104f05e999ebf52a0/README.md). The SDK has its own [Modified MIT license](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/LICENSE); it is an optional consumer dependency, not bundled into OPFS VFS.

This library change depends on website PR #9's base, not the parallel DuckDB implementation. The branch can be added above the agreed stack tip after coordination. It adds no website demo or runtime networking layer. Nothing was merged or published.

## Extension options without changing EdgeJS

The EdgeJS guest can remain the official, unchanged registry package. The missing extension belongs in the Wasmer host. The custom-host option has since passed the [live-mount probe](edgejs-live-opfs/README.md); the other alternatives below remain architectural options.

- Keep the shipped snapshot adapter. This requires no host rebuild and is a verified option. Wrapping `sandbox.fs` does not intercept guest system calls.
- Maintain a version-pinned patch and reproducible build of the Wasmer SDK. This avoids creating a repository fork or waiting for an upstream merge, but still owns a modified host artifact. It needs browser mount wiring, a worker-safe OPFS bridge, and JavaScript bindings. A JavaScript-only package patch is insufficient.
- Build a separate host package on upstream Wasmer/WASIX libraries. This can leave both upstream repositories untouched, but must own the lower-level runner and browser worker integration because the high-level SDK does not enable external providers in browser builds. It cannot attach a new provider to an already-created stock npm SDK instance.

The provider contracts require `Send + Sync` and the existing adapter [blocks on a channel while provider futures execute](https://github.com/wasmerio/wasmer-sdk/blob/9ca7da8a3b34c4073a068231cc89b4a8416084b2/rust/src/provider_fs.rs#L825-L862). The follow-up owner-worker probe verifies browser progress with a synchronous bridge; it does not reuse this blocking async-provider adapter. A guest-side `node:fs` replacement would cover only the operations routed through that replacement; EdgeJS's [built-in filesystem module uses internal bindings](https://github.com/wasmerio/edgejs/blob/7027edfa748d9b5e2f6beba104f05e999ebf52a0/lib/fs.js#L67), so it is not a general filesystem-provider extension.
